对 soroban 全栈（后端 / 前端 / 迁移 / 爬虫插件 / 启动脚本）做的一轮系统审计：SQL、输入校验、
各页功能与交互、跨层一致性、并发、性能。**已修的写在「一、已修」；需要你拍板的写在「二」；
命名歧义写在「三」；优化方向写在「四」。**

审计基线：`fcd31a8`（含 `ceee9b7` 引入的「集运中/已到达」状态改造与集运 OCR）。
新增回归测试 372 条，全绿；前端 `npm run build` 通过；后端真实起服务冒烟通过。

## 一、已修

### 1. 【高危 · 数据静默丢失】爬虫回灌的订单状态被后端整批拒绝

`ceee9b7` 把订单状态 `交易成功` 改名为 `已签收`（并新增 `集运中`/`已到达`），但爬虫插件
`taobao_scraper/normalize.py` 的 `STATUS_MAP` 仍映射到 `交易成功`。

后果：淘宝页上处于 **交易成功 / 待评价** 的订单，回灌时 `order_status` 撞上
`StagingBase` 的枚举白名单 → 422 → 被 `soroban_client.upsert_orders` 计入 `skipped` 静默跳过。
日志只会看到 `skipped` 数字变大，不会报错。**已完成的订单从此再也同步不进来。**

修复：`STATUS_MAP` 的两个目标值改为 `已签收`，并在该文件写明「右侧的值必须是后端 OrderStatus
现存字面量」。同时新增 `test_consistency.py::test_scraper_status_map_targets_are_valid` 守住这条
跨仓约定——这个 bug 就是它抓出来的。

### 2. 【高危 · 功能失效且反馈失真】OCR 按订单号合并时，成交价被静默丢弃

商品订单页的「同一单先后拍多张截图逐步补全」流程里，`buildMergePatch` 把 `price_cny` 放进
PATCH。但 `price_cny` 是**派生列**（= Σ单价×数量 + 邮费），后端 `update_order` 明确把它从写入
字段里排除；而这次 PATCH 又没带 `items`，于是价格**原样被丢掉**——界面却弹「已按订单号匹配更新」。

复现：建一张只有订单号的单（自动占位物品、价 0）→ 再拖一张含成交价的截图 → 价格仍是 ¥0。

修复（`frontend/src/views/Orders/index.vue`）：改价必须走物品。把成交价当**种子价**、连同一份
「都不带单价」的物品一起发过去，由后端 `build_items` 用与新建单同一套规则折成单价。并加
`hasNoRealPrice()` 守卫：只有「物品全是系统占位(auto) 且合计为 0 且无邮费」的单才回填，
用户手填过任一单价的单绝不覆盖。后端侧两条行为已用测试钉死。

### 3. 【中高危 · 双引擎发散】31 个 VARCHAR 列没有长度校验

所有 str 列都是定长 VARCHAR（`order_no(64)`、`shop(255)`、`platform(32)`…），但输入 schema 里
只有 `TagIn.value` 声明了 `max_length`。超长输入在 **SQLite 上静默照存**、在 **MySQL 上直接
`Data too long` → OperationalError → 500**。这正是代码库自己反复想避免的「双引擎发散」
（`TagIn` 的注释写了这个理由，只是没推广到其它列）。`ShipmentOrder.weight`（`Numeric(8,2)`）
同样没有上限校验，MySQL 会 `Out of range`。

修复（`app/schemas.py`）：
- 新增 `_len(model, column)`——长度**以建表定义为唯一真相**，改列长不必再改校验；
- 标识类列（订单号/快递号/账号/平台/收货人/国际单号…）超长 → **422**；
- 自由文本列（商品标题 `shop`、物品名 `name`、杂项名）超长 → **截断**到列长。
  理由：爬虫会把一单多件的标题拼成「A / B / C」、用户会整段粘贴商品页文案，
  一刀 422 会把整批同步打回；截断只损失尾巴，且与 `build_items` 里既有的 `[:255]` 同口径；
- 顺手把 `_q_money` 抽成 `_q_decimal(v, max, quantum, label)`，`weight` 复用同一条通道；
- `OrderCreate/OrderUpdate`、`ShipmentCreate/Update`、`MiscCreate/Update` 里重复的字段声明
  收敛成 `OrderFieldsIn` / `ShipmentFieldsIn` / `MiscFieldsIn` 三个 mixin（原本 Create 与 Update
  各写一份，正是长度校验容易只加一半的地方）。

`test_lengths.py` 里有一条**元测试**：遍历模型的每个 VARCHAR 列，检查对应输入字段要么声明了
等长 `max_length`、要么在「截断」白名单里。以后加列忘了加校验会直接红。

### 4. 【中危 · 部署】`backend/.requirements.sha256` 被提交进版本库

这是「本机装了哪一版依赖」的指纹，被误提交且内容已过期（对不上现在的 `requirements.txt`）。
危险在机制本身：一旦某次提交的指纹恰好等于 `requirements.txt` 的哈希，别人 clone 下来
`start.bat` 就会认为「依赖已是最新」而**跳过 `pip install`**，得到一个什么都没装的环境。
另外 `start.sh` 把指纹放在 `.venv/` 里、`start.bat` 放在 `backend/` 下，两边位置还不一致。

修复：从版本库移除 + 加进 `.gitignore`；`start.bat` 改放 `%CONDA_PREFIX%\.soroban-requirements.sha256`
——**指纹跟着它描述的那个环境走**，而不是跟着源码走。

### 5. 【性能】三个列表接口都是 N+1

- `GET /api/shipment`：每个集运单单独查一次子订单。更糟的是 `ShipmentRead.model_validate(order)`
  为了填 `orders` 字段会去**懒加载关系**，把该集运单**含已软删的**全部子订单拉出来，
  紧接着又被过滤过的列表整个覆盖——纯白跑。
- `GET /api/staging`：每行 `session.get(Order, ...)` + 每单懒加载 `items`。一屏 100 行 ≈ 200 条 SQL。
- `GET /api/orders`：`OrderRead` 带 `items`，每单一次懒加载。

修复：`_read_many()` 批量化（一次 `IN` 查询 + `selectinload` 取物品）；集运侧新增 `_shipment_read()`
只用本表列构造、绝不碰关系属性；订单/暂存列表加 `selectinload`。

实测（`test_queries.py` 用 `before_cursor_execute` 数 SQL）：集运列表 2 行 7 条 → 8 行 13 条，
修复后**恒定不随行数增长**。`test_queries.py` 会持续守住这条。

### 6. 【一致性】软删不推进 version / updated_at

单条软删只置 `is_delete=True`，而按账号批量软删（`soft_delete_account_orders`）会
`version+1, updated_at=now`。两条路径语义不一，且 `updated_at` 记不到「什么时候被删的」——
数据库层排查/恢复时少一条线索。修复：`soft_delete()` 统一推进。已验证不影响「软删后订单号可复用」。

### 7. 其它

- `import_staging` 的并发门闸失败分支补 `session.rollback()`：原来靠 `get_session` 退出时
  `Session.close()` 隐式回滚，但那之前刚 `flush()` 过一张 Order，把「不提交」写成代码而不是
  依赖调用方的清理顺序。
- `GET /api/tags/{field}` 一个请求里把 `_data_values`（几张表的 DISTINCT 扫描）跑了两遍
  （`_sync` 补登记一次、算 `in_use` 一次）→ 改成算一次共用。
- `run_migrations` 里 `check_engine` 的释放条件恒真却写成了条件判断，读起来像「有时不释放」
  → 简化并注明必须释放（否则每次迁移漏一个连接池）。
- `list_orders` 的 `id` 参数遮蔽内建 `id()` → Python 侧改名 `only_id`，对外仍是 `?id=`（前端不用改）。
- `NotionTable.vue` 的 `dirtyDuringLoad` 是死代码：它只在 `saveLayout()` 里被置 true，而
  `saveLayout()` 又被 `layoutReady` 门控、`layoutReady` 到布局拉取完成才置 true——永远不可能为真。删除。
- `build_items(items_in, seed_total, shop)` → `build_items(items_in, seed_goods, fallback_name)`：
  第二个参数在**所有**调用点传的都是「货款」（已扣邮费），叫 `seed_total` 会诱导下一个人传总价，
  从而把邮费重复计一次；第三个参数实际用途是「没有物品明细时拿来当物品名的商品标题」。
- 「点选挂靠」不改订单状态、而「内含快递 OCR 挂靠」会推进到`集运中`——查证后认为这是**有意的
  业务区分**（点选=打算放进这个包裹，货未必已到仓；OCR 来自集运方装箱清单=货确实在包裹里），
  不是遗漏。但两条路径读代码时看不出这层区别，已在 `attach_order` 文档串里写明，并加了两条
  测试把「挂靠/解除都不动状态」钉住。
- README 的「其余回退到前端」不准确：`StaticFiles(html=True)` 对未知路径返回 404 而非 index.html。
  当前用 hash 路由（`/#/orders`）所以不受影响，已在 README 注明——**若将来改 history 模式必须补兜底**。

## 一之补：A/B/C/D 四项已按最优解落地（第二轮）

> 原「需要拍板」清单里的 A、B、C、D 已实现，做法与理由如下；E、F 仍待定，见「二」。

### A. 自由文本超长 → **把列放宽，不再截断**（迁移 `d0e1f2a3b4c5`）

原方案是「截断 or 422」二选一，其实两者都在损失：截断悄悄丢字，422 打回整批同步。
真正的问题在**列本身**：`orders.shop` / `orderstaging.shop` 存的是**商品标题**，一单多件时
爬虫会拼成「A / B / C」，天然超过 255；而这两列既不做索引也不参与唯一约束，定长毫无意义。
现改为 `TEXT`，输入层不再截断、也不会 500，一个字都不丢。

SQLite 侧刻意不做 DDL——它本来就不强制 VARCHAR 长度，跑 batch ALTER 反而要重建表、
有搞坏部分唯一索引的风险。物品名/杂项名仍保留 255 + 截断：那是显示标签，255 远超所需。

### B & C. 种子价**只**认本次显式传来的 `price_cny`，不再回退到当前价

两条问题同源：`update` 里 `seed = payload.price_cny ?? 当前价`。去掉回退后一起消失：

- **B**：清空全部单价 → 现在一律记 0 + auto（灰显待补价），**与「只清空部分单价」同口径**。
  旧行为是把旧总价整个折到第一条上——同一个动作两种结果，才是真正别扭的地方。
- **C**：改邮费 + 送无单价物品 → 不再拿「旧总价 − 新邮费」倒推货款（那会让总价看着没变、
  货款却悄悄改了）。无单价就是无单价。

显式给种子的路径（爬虫、OCR 补价）完全不受影响，仍按原规则折算。
只保留一处回退：订单**一条物品都没有**时的兜底补位——那时价格只存在于订单行上，不接过来就丢了。
顺带把散在 6 处的「订单价 − 邮费」换算收敛成 `routers/common.goods_seed()`。

### D. 单号写入即归一（迁移一并补齐历史数据）

- `express_no` / `intl_tracking_no`：**TRIM + UPPER**。它们是匹配键（集运「内含快递」截图靠
  `express_no` 精确匹配商品订单），而 OCR 提取时已 `.upper()`、用户手输可能小写带空格，
  加上「SQLite 区分大小写、MySQL 默认不区分」，不归一就是双引擎发散。这两列无唯一约束，
  历史数据可安全批量改写。
- `order_no` / `shipment_no`：**只 TRIM，不改大小写**。这两列有唯一索引，批量改大小写可能撞约束
  让升级直接失败；而它们实际是纯数字/「数字-数字」，大小写本就不是问题。去空格则纯赚——
  粘贴带来的首尾空格会让唯一约束形同虚设（`" 123"` 与 `"123"` 被当成两张单）。
- 空白串统一归 `NULL`，否则 `IS NOT NULL` 之类的过滤会把空值当有效值放行。
- 查询侧（`?express_no=` / `?order_no=`）用同一套 `norm_code` / `norm_id` 归一，
  避免「写进去归一了、查的时候没归一」。

新增 `test_code_normalization.py`、`test_migrations.py`（含从旧版本升级 + 脏数据归一的端到端验证）。

## 一之补二：多智能体全项目审计（第三轮）

10 个维度并行只读审读全仓 → 57 条发现 → 逐条对抗性证伪 → **确认 21 条、证伪 9 条**。
（证伪的那 9 条里有一条很值得记：有人报「集运 OCR 路由把读事务开着 await 数秒」，
复核发现 pysqlite 默认只在写语句前才发 BEGIN，SELECT 跑在 autocommit 下——根本没有快照，
实测也复现不出来。这类「框架语义误解」是审计里最常见的误报源。）

### 最高危：打包分发的 exe 是开箱即用的认证绕过（3 条发现同一根因）

`soroban.exe` **从不生成 `.env`**——生成随机 SECRET_KEY 的代码只在 `start.sh`/`start.bat` 里，
两者都不参与打包。于是分发出去的 exe 用 `config.py` 里那个**写在公开仓库里的默认密钥**签 JWT，
`main.py` 对此只 `log.warning` 就继续跑；同时默认 `HOST=0.0.0.0` 全网卡监听、每次启动自动播种
`admin/admin123` 并把口令打印到控制台、登录端点无任何限速。
同网段任何人 `jwt.encode({"sub":"1"}, "dev-insecure-key-change-me")` 就是管理员——可读写全部账本、
`/api/db/switch` 切库、`/api/plugins/{id}/fetch` 在宿主机上起子进程。拿到 `soroban.db` 的人还能用
同一常量解出加密的 MySQL 连接串。

已修（四层，缺一不可）：
1. `run.py` 首启就地生成含 `secrets.token_hex(32)` 的 `.env`，且**在 import app 之前**
   （`app.config` 导入即读 `.env`，顺序反了等于没生成）；
2. `HOST` 默认改 `127.0.0.1`，要暴露得显式设；
3. `main.py` 对不安全 SECRET_KEY **fail-closed**——直接拒绝启动。这类问题没法「登录进来再修」
   （令牌本身就不可信），所以不适合像默认密码那样只告警；
4. 登录失败退避（`app/ratelimit.py`）：前 5 次不罚，之后指数退避封顶 5 分钟，按
   (用户名, 来源 IP) 计数、成功即清零、退避期内**密码正确也挡**。
   实测：第 6 次失败起退避、第 7 次 429 带 `Retry-After`，换个用户名不受牵连。
5. `run.py` 不再打印默认口令。

## 二、需要你拍板

### E′. 迁移与切换之间没有写屏障 —— ✅ 已修（按用户方案实施）

**用户定的方向**：拷贝时锁库、停一切写入；拷完解锁，之后的改写就写旧库；切换那一刻来不及的少量数据可接受。

**实施时补强的两点**：

1. **锁库不只是防手滑，是必需的**——`replace_data` 逐表读源库，而 SQLite 侧**没有读快照**
   （pysqlite 默认只在写语句前才发 BEGIN，SELECT 跑在 autocommit）。拷贝中途的写入会产生
   **撕裂的拷贝**：订单拷过去了、它的物品没拷；或子表引用了尚未拷贝的父行。
   源库是 MySQL 时反而一致（pymysql 的 SELECT 会开事务、InnoDB 给整轮快照）——又一处双引擎发散。
2. **「丢的只是爬虫能爬回来的」不成立**。W1 还会丢：OCR 建的闲鱼订单、集运单、杂项、
   **以及所有编辑**（改价/改状态/挂靠/导入）、标签、列布局。而且是**静默**的：切换成功、无报错。
   → 加了一层**变更检测**，把静默丢失变成知情选择。

**落地**：

- `app/maintenance.py` 只读屏障，覆盖**三条写路径**（只拦 HTTP 是不够的）：
  ① HTTP 写端点（`main.py` 中间件，`/api/db/*` 与登录放行）——用中间件而非逐端点挂依赖，
  将来新增的写端点自动被覆盖；② `fx_loop`（直接用 Session 写 FxRate，绕过 HTTP）；
  ③ `scheduler_loop`（屏障期间别起爬虫子进程——白开一次浏览器冲淘宝，而并发多开是风控红线）。
- **绝不泄漏**：try/finally + **硬超时自愈**（15 分钟）。宁可迁移中途失去保护（最坏是拷贝撕裂、
  可重来），也不能让用户对着一个再也写不进去的账本。挂起时还会等在飞的写请求排空。
- **变更检测**：`migrate` 拷完记一份源库指纹（各表行数 + 最大 `updated_at`，存控制库的
  `migrate_state` 表，按目标分行）；`switch` 前再算一次比对，不同就 409 并说人话：
  「迁移之后当前库又有改动（商品订单 +3 条、集运订单 有改动）」。
  前端弹二选一：**重新迁移再切换**（默认）／仍然切换（放弃这些改动）。
  指纹刻意不含 `columnlayout`——拖一下列宽不该触发告警。

**顺带修出一个真 bug**：新增 `migrate_state` 控制表后全部测试瞬间全红——`run_migrations` 判定
「pre-Alembic 旧库」的排除集是**手抄**的 `{app_db_config, db_connection, alembic_version}`，
新控制表没进去 → 全新部署被误判为旧库、stamp 到 baseline 而建不出业务表。
已改为**从 `control_metadata.tables` 自动派生**，并加测试锁住（再写成手抄清单就红）。

### E. 登录接口没有速率限制 —— ✅ 已修（见「一之补二」）

`/api/auth/login` 可无限次尝试。本机自用无所谓；README 里已提示「局域网/多人使用前务必改默认密码」。

## 六、SQL 方言专项审计（第四轮）—— ✅ 已全部修复并在真 MySQL 上验证

10 维度并行排查 + 双视角对抗证伪（33 条原始发现 → 去重 18 条 → 18 条存活）。
拿到真 MySQL 9.7 之后把全部推演逐条实测，结论收敛为**一个根因 + 6 个独立缺陷**。

### 根因：MySQL 侧字符串列全落在 `utf8mb4_0900_ai_ci`，SQLite 是 BINARY

`53b7e33debd0_baseline_schema.py:30` 的 `_MYSQL = {"mysql_engine": ..., "mysql_charset": "utf8mb4"}`
只给了 CHARSET 没给 COLLATE。MySQL 的规则是「表声明了 CHARACTER SET 却没声明 COLLATE 时，
取该**字符集**的默认排序规则」——不是库的，所以 `ensure_database` 里那句
`COLLATE utf8mb4_unicode_ci` **从来没生效过**（何况它本身也是 `_ci`）。

实测 MySQL 9.7 判为相等：

| 比较 | `_0900_ai_ci` | `utf8mb4_0900_bin` | SQLite BINARY |
|---|---|---|---|
| `'Alice' = 'alice'` | 相等 | 否 | 否 |
| `'José' = 'Jose'` | 相等 | 否 | 否 |
| `'ＡＢＣ' = 'ABC'` | 相等 | 否 | 否 |
| `'ヤマダ' = 'やまだ'` | 相等 | 否 | 否 |
| `'ｶﾞ' = 'ガ'` | 相等 | 否 | 否 |
| `'a ' = 'a'` | 否 | 否（NO PAD） | 否 |

对一个日本代购账本，命中面远不止「大小写」。两条实测复现的后果：

1. **迁移被彻底卡死**：SQLite 里合法共存的两个标签拷进 MySQL 撞 1062，`replace_data` 是
   单事务 → 整次迁移回滚。且 UI 里无法自救：删标签 409「正被数据使用」、改名 409
   「新名字已被占用」，只能手工进库改。
2. **批量改名误伤**：`WHERE col = value` 在 MySQL 上命中变体行。实测「改一个收货人
   `Alice→Alicia`，另一个 `alice` 被一起改成了 `Alicia`」。同理 `delete_account_staging`
   会硬删掉另一个账号的暂存行（连同 `StagingItem`，不可恢复）。

**修法**（迁移 `f2a3b4c5d6e7`）：`dialect.BinStr(n)` 给 11 个键列在 MySQL 上显式声明
`utf8mb4_0900_bin`，`emit_active_unique` 的 3 个生成列同样带上。顺序必须是
**拆生成列 → 改基础列 → 重建**。SQLite 侧零 DDL。
选 `_0900_bin` 而非 `utf8mb4_bin`：实测 `SHOW COLLATION` 后者是 **PAD SPACE**，
只有前者 NO PAD 才与 SQLite BINARY 等价；`bin_collation()` 在老服务端探测后回退。

## 十三、第七轮多专家对抗审计（28 agent / 18 维度）—— 已修

审计 workflow 产出 40+ 条，经双视角对抗证伪后综合成 A1–A30。以下是**已改完**的部分，

### 架构结论（审计的独立判断，与我一致）

> **主系统↔插件的边界画对了，不该动；坏掉的是穿过边界的胶水层。**
> 同一个动作「跑一次插件」被拆到 `issue / launch / reap / revoke` 四处，没有任何对象持有它，
> 而触发路径有三条。本轮确认的 P0/P1 **全部**落在这里，一条都没落在被划分开的两侧。

三条硬证据：边界画在**变更频率**上；默认拒绝的闸门验的是**真实路由表**而非第二份前缀表
（挡住了 `POST /api/staging/{id}/import` 挂在 staging 前缀下却是「直接建账本单」这个真陷阱）；
结构守卫是这套形状真正的支撑物，进程内插件写不出这类断言。

### A1 · 多账号扇出共用一枚令牌（P0）

整个扇出只 `issue` 一次，而 `_reap` 结束时 `revoke(jti)` —— **先跑完的账号把还在跑的兄弟全部踢下线**。
不需要任何失败，各账号耗时天然不同就会中。淘宝插件是抓完才一次性回灌，慢的那个「爬完了、
推的时候全 401」，整批订单丢，而且是静默的。改成一进程一枚。

### A2 · 定时抓取不下发插件参数（P0，本轮唯一会写坏账本数据的一条）

只有手动路径带 `params`，定时那条只发 `plugin_settings()`；而 fx 清单写的是 `settings = []`
→ 返回 `{}` → `_launch` 里 `if config:` 判假 → `SOROBAN_CONFIG` 干脆不设置 → 插件全部回落内置默认。
**后果不是报错**：fx 一天四轮，当天取「手填优先、其次最后一条」，用户手点的那条几乎必然被定时条盖掉——
卡片上显示着用户设的源，写进账本的却是默认源。抽出 `_launch_conf()`，两条路径共用一份。

### A3 · 暂存页写穿账本不补汇率（P0）

暂存页的汇率格可编辑且可清空，清一下 PATCH 过去 `fx_rate = null`，
`jpy_auto/jpy_settled` 一起变 NULL → 看板 SUM 跳过、笔数照数，「笔数 +1、金额 +0」。
`stamp_fx` 自己的 docstring 就写着「必须在 create 和 update 两处都调」，orders/misc/shipment
三处都有这一刀，只有这条路径漏了。

### A4 · 集运单缺汇率时运费被吞掉，只剩特殊费冒充结算额（P1）

`elif extra_jpy: auto = extra_jpy` 这一支在「有运费、无汇率」时也会命中：
界面显示一个**看起来完整**的金额（只有特殊费），运费部分永久缺失并被看板加总；
而商品订单同场景显示「—」，一眼看得出缺口。判据用真值不用 `is not None`——
否则「运费显式填 0（预付/包邮）+ 特殊费」会被打成 None，修一个丢钱的 bug 反造一个。

### A6 · 定时任务的成败在界面上完全不可见 · A7 · `/fetch` 绕过「启用」总开关

`/fetch` 与 `/login` 两个写死动词的端点同时踩了四个坑：绕过总开关、不校验命令 needs、
不下发参数、扇出共用令牌、还不写回结果。**审计倾向降级成薄壳，我选了删掉**——
它担心的「丢掉临时抓一个已停用账号」这个能力，我在 `run_command` 里显式保住了
（点名 account 时不看启用位）。三条启动路径变一条，A2/A6/A7 一次性消失。

### A8 · 令牌恒 12 分钟，收割器等 30 分钟

`scopes.issue` 三个调用点全用默认 `timeout_s=600` → TTL 720s，而 `communicate(timeout=1800)`。
**任何超过 12 分钟的抓取，最后那次回灌必然 401**，单账号也中。提出 `_REAP_TIMEOUT` 常量，
TTL 由它推导；`_HARD_TTL` 从 30 分钟提到 40 分钟——取 30 会让令牌与进程同刻到期，等于没修。

### A9 · 物品删除失败不回滚（P1）· A10/A11/A12/A21

- **A9**：删除先动本地数组、失败不放回去 → 下一次任何成功的保存都会把「不含它的 items」
  整体覆盖上去，这条物品和它的钱被静默删掉。同文件的 `commitDraft` 早就这么做了，这里漏了。
- **A10**：`fx.rate` 同轮去重键漏了 `source`，且 `date or "today"` 让「不填」和「显式今天」
  变成两个键——**两个方向都错**，都表现为静默丢数据。
- **A11**：`manual` 在核心里是语义关键字（当天优先、显示「手填」、写侧挡自动源），
  但 ingest 只校验字符集，插件可以用它冒充手填。加一条拒绝。
- **A12**：`load_kinds()` 挂在只读屏障中间件第一行（连 GET 都走）。注册失败时
  **每个请求都重试、每个请求都 500**，栈顶是屏障不是注册点，表现成「服务起来了然后全站 500」。
  搬到模块级——不放 lifespan，因为 conftest 的 client 夹具明写不进 lifespan。
- **A21**：命令按钮的 `blocked` 用裸 granted，执行闸用 `token_scopes`。
  作者把 needs 写成没在顶层声明的项时，按钮永远灰、勾选框里又没那项可勾，用户无解。改成同源。

## 十四、需要你拍板（第七轮）

### T2 · MariaDB / MySQL 5.7 支持：修代码还是改文档？

`dialect.py` 的 `BinStr` **硬写** `utf8mb4_0900_bin`，绕过了 `bin_collation()` 的探测回退。
唯一用 `BinStr` 建表的迁移 `b0c1d2e3f4a5` 会在 MariaDB 上 `ERROR 1273`，而前面的迁移
DDL 已隐式提交、库停在半升级态。但 `README.md` 白纸黑字承诺「MariaDB 会自动回退」。

- **A**：改那个迁移，建表期现算 `bin_collation(op.get_bind())`
- **B**：删掉 README 的承诺，明写「需 MySQL 8.0+」
- **明确否决**：把 `is_mysql` 收窄成 `== "mysql"` —— 所有分支都是 `if is_mysql() … else <SQLite 分支>`，
  收窄后 MariaDB 会掉进 SQLite 分支被喂它不认的语法，失败得更早也更难懂
- **倾向 B**：你会不会把 soroban 指向 MariaDB（NAS 自带那种）只有你知道。不会的话 A 的期望收益是 0。
  **注意：MariaDB 的 1273 从未在真机验证过**，判断来自代码与 README 的自述。

### T3 · 汇率写侧「手填当天拒收自动源」：保留还是改成追加 + 读侧取舍？

项目自己两处矛盾：`fx_rate.py` 在**写侧**拒收，而 `fx.store/pick_from` 的 docstring 都写着
「写侧只管追加、读侧取舍」。拒写的代价是汇率页那天的 `count/low/high/sources` 全部失真
（追加式存储的立项理由就是「回看那天几点是多少」）。
**倾向保留拒写**——改成追加就必须连 `GET /api/fx` 与看板一起从 `latest_stored` 改成 `pick_on`，
否则顶栏与账本当场显示两个数。账本金额一分不差，实际损失只有「一年几次的那一天少列几行」。

### T4 · `_reap` 的成败判定：信退出码还是信插件回的 JSON？

taobao 的 `run.py` 明写「有失败就非零退出」、`already_running` 刻意 `return 0`——
**这是跨进程契约不是疏忽**。改成信 JSON 会把插件作者刻意的软跳过刷成红色。
**倾向保持现状**，只改显示：摘要里含 error 时给卡片一个中性色（黄）而不是绿。

### T5 · `data:own` / `PluginRecord` 全套：给期限还是现在删？

零消费者（两个 plugin.toml 都没声明，`GET /records/{kind}` 对人登录直接 400）。
**倾向给期限（半年）而不是现在删**——删它要动迁移，比留着贵。但建议**现在**修掉
`json.loads` 与 `limit` 边界：零消费者时改最便宜，一旦有第一个真消费者，格式就再也改不动了。

### T6 · 未导入暂存行可 PATCH 成「已导入」

前端该列 `readonly`、插件的 `_PUSH_FIELDS` 不含该键，但端点挂 `staging:write`，
持该权限的令牌在协议上可以发。后果可逆（仍能被 `/import`、`/ignore` 救回）。
**倾向只补注释**：把 `import_status` 从未导入分支剔掉，等于关掉今天唯一一条
「待处理 → 已忽略」的 PATCH 通道。

### T7 · `stale` 与 `expired` 的命名（我加的一条）

`FxRead.stale` = 不是今天的（日粒度），`is_expired()` = 超过 `fx.stale_hours`。
两个词在英文里同义，在这里是两回事——而**驱动 `expired` 的设置却叫 `stale_hours`**。
建议 `fx.stale_hours` → `fx.expire_hours` 且 `FxRead.stale` → `not_today`，
但前者是持久化的 prefs 键，要带兼容读取，所以不擅自动。

### T8 · 单进程假设没有任何断言保护

撤销表 `scopes._ALIVE` 在进程内。今天成立只因为 `run.py` 是单进程 uvicorn；
一旦 `workers>1` 或 `--reload`，插件全线 401。要不要加一条启动断言（发现多 worker 就拒绝启动）？

### A5 · 汇率插件把「一条都没写进去」报成绿色成功

### A23/A25 · 插件私有存储的边界

## 十九、认证与会话（第 2 轮，上一轮声明未审的区域）

### 登录退避可被伪造的 `X-Forwarded-For` 完全绕过 —— 真机实测确认

uvicorn 默认信任来自 loopback 的代理头（`forwarded_allow_ips="127.0.0.1"`），
而前端开发代理、以及**任何同机反向代理**都会让后端把每个请求都看成来自 127.0.0.1。
于是 `request.client.host` 变成攻击者可控的字符串，每换一个值就是一个全新的退避键。

实测（起在 8641 端口，SQLite 副本）：

```
固定 XFF 打 12 次： 401 401 401 401 401 401 429 429 429 429 429 429
轮换 XFF 打 12 次： 401 401 401 401 401 401 401 401 401 401 401 401   ← 一次都没挡住
修复后轮换 12 次： 401 401 401 401 401 401 429 429 429 429 429 429
```

改法：退避**同时按两个键**计数——`(用户名, IP)` 与 `(用户名, "*")`，取更严的那个。
第二个键让伪造 IP 变得毫无用处，同时保留「不同用户名互不牵连」。

### 「先查退避、再记失败」不原子

两次独立取锁，中间有窗口：并发一发，一个退避窗口能塞进几十次口令尝试
（实测破坏版放行 16 次，上限应为 6）。改成只暴露一个 `begin()`，在同一把锁里判定并计数——
宁可把一次成功登录也先记上一笔，成功后 `record_success()` 清零。

### 用户名枚举时序信道

不存在的用户名直接短路、根本不跑 bcrypt。实测修复前 7ms vs 294ms，一个数量级，
100% 可判别。加一次「陪跑」bcrypt。附带收益：`ratelimit._prune` 的注释里写着
「猜不存在的用户名几乎零成本」正是挤兑退避表的手段——那条路一起变贵了。

### `/docs` 与 `.env` 权限

- `/docs`、`/redoc`、`/openapi.json` 无需认证，`HOST=0.0.0.0` 时等于把完整 API 面
  （含每条路由的插件 scope 标注）给整个局域网看。改成**只在监听环回时默认开**，
  绑到局域网要显式 `SOROBAN_DOCS=1`。不是一刀切关掉——环回下它没有这个问题且平时很有用。
- `start.sh` 生成的 `backend/.env` 是 0644，而 `run.py` 做同一件事时 `chmod 600`。
  里面有能伪造管理员令牌的 `SECRET_KEY` 与数据库口令。同一个文件由谁生成决定它是不是
  全机可读，是最难注意到的那种不一致。

但 TestClient 的 `request.client.host` 恒为 `"testclient"`，XFF 根本不参与，

## 二十、OCR 与前端业务正确性（第 2 轮）

### 「内含快递」截图重传不幂等 —— 重传一次，别人正在编辑的单就 409

WHERE 里放行了「已挂本单」以求幂等，但 SET 里带着 `version + 1`。于是**幂等只对挂靠关系成立、
对乐观锁不成立**：同一张截图传两次，这些订单的 version 就 +1，正在编辑其中某单的人
下一次保存直接 409，而他什么都没做错。改成已挂本单时一个字节都不写。

### 又一条假绿守卫（这次是别人写的）

`test_ocr_auto_attach_does_not_write_status` grep 源码里有没有 `'"status"'`（**带引号**）。
列名改成 `purchase_status` 之后，`"purchase_status"` 里根本不含 `"status"` 这个带引号的串，
**断言永远不可能触发**。换成实际跑一次挂靠、比对 `purchase_status` 有没有被动过。
顺带补了一条重传幂等的行为测试。

### 侧栏计算器：大数算错 + `Infinity` 泄漏

去浮点尾巴那步写的是 `Math.round((x + EPSILON) * 1e10) / 1e10`：

```
922337205  →  旧: 922337204.9999999   新: 922337205
Infinity   →  旧: "Infinity"          新: （空）
0.1+0.2    →  旧: 0.3                 新: 0.3          （显示口径不变）
1/3        →  旧: 0.3333333333        新: 0.3333333333 （显示口径不变）
```

`x * 1e10` 超出双精度能精确表示整数的范围后，**本来是想去尾巴的那一步自己制造了尾巴**；
再大一点直接溢出成 Infinity，而 `isFinite` 是在放大**之前**查的，于是结果框里出现字符串
"Infinity"。改用 `toFixed(10)`——在十进制字符串上截断，不放大，既不溢出也不引入误差，
且显示口径与原来逐字一致（上表验证过）。

### 订单页隔离视图混入新建行

处于 `?focus=<id>` 隔离视图时用幽灵行新建，订单会被 unshift 进隔离列表、total 从 1 变 2，
**刷新一下又凭空消失**——用户会以为刚才那单没存上。
`clearFocus()` 原先只在 OCR 那条路径上调，手工新建这条漏了。移进 `addRow` 本身，
两条路径（以及以后任何新入口）自动都对。

### 21.1 金额正确性（本轮最贵的一条）

**`build_items` 的种子价折算会把整单金额算错，最坏能翻倍或归零。**
`backend/app/routers/common.py`：订单价是 `Σ(单价×数量)` 派生的，而单价用
`(种子/数量).quantize(HALF_UP)` 取整——乘回数量就不等于种子价了：

| 种子价 | 数量 | 旧单价 | 旧总价 | 差 |
|---|---|---|---|---|
| ¥100.00 | 3 | 33.33 | 99.99 | −1 分 |
| ¥5.00 | 1000 | 0.01 | **10.00** | **翻一倍** |
| ¥0.40 | 1000 | 0.00 | **0.00** | **整单归零** |

后两种在「一批小商品按件录数量」时真实可达，且**没有任何提示**。
改法：`ROUND_DOWN` 取整（保证余数非负）+ 余数单独成一条「（金额尾差）」行 ⇒ 总额精确。
尾差行 `auto=True` 灰显，跟其余待拆分的行同待遇，复核的人一眼看得到那一分钱去哪了。

**这条被一条测试当成「已知行为」钉了很久**（`test_seed_split_rounding_may_shift_cents`，
注释写着「已知且被 backfill 工具文档化的行为」）。教训写进了 `tests/README.md`：
往「已知取舍」里加断言之前，先问一句「它的最坏情况有多坏」。

顺带：`tools/backfill_item_price.py` 自带了**第二份** `build_items` 规则（第 1 轮就记过
这个隐患）。改一侧不改另一侧，同一批数据经两条路径会得到不同总价——所以改成直接调
`build_items`，规则只留一份，容差从 `0.01×数量` 收紧到 **0**。

**邮费校验的口径也修了**：`_check_postage_within_total` 原先只在 `not items` 时生效。
可 `build_items` 走种子路径的判据是「有没有物品**带单价**」——「传了 3 条没单价的物品」
和「一条都没传」是同一条路径、同样会把货款夹到 0 再把总价抬成邮费。
于是同一个非法输入（邮费 > 总价）在前者是 422、在后者是 200 + 静默改额。

### 21.2 插件权限：`needs` 原先只用来禁按钮，令牌照发全量

`run_command` 与 `_run_due` 都用 `scopes.token_scopes(m, cfg)`（插件的**全部**授权）
签令牌。于是 `needs = []` 的「只测试、不写入」命令拿到的是能写暂存表、能改汇率的完整令牌
——卡片上写着这条命令不需要任何权限，实际下发的却是插件的全部能力。
改成 `granted & set(cmd.needs)`。少声明的命令会收 403 而不是悄悄越权，那是正确的失败方向。
（核对过：`fx probe`、`taobao login/status` 都不调核心接口，收窄后不受影响。）

同一处还修了两条**手动/定时口径分叉**：
- **扇出规则有两份**：手动看 `cmd.per`，定时看 `manifest.accounts`。同一条 `per` 未声明的
  命令，手动跑一次、定时按账号跑 N 次并多带 `--account X` ——插件收到一个它在手动路径下
  从未见过的参数组合，而差异只出现在无人值守那条路上。收敛成 `_fan_targets`，`_fanout` 删除。
- **多账号扇出的结果互相覆盖**：N 个子进程共写 `PluginConfig` **同一行**的
  `last_outcome/last_summary`，谁后完成谁覆盖。「3 个号里 1 个登录过期」这件事，
  只要那个号先跑完，卡片上就只剩最后一个成功号的绿字——失败的账号在界面上完全消失，
  而它恰恰是唯一需要人去处理的那个。改成按批次聚合，未完成时显示「k/N」，
  全完成后逐个列出，有一个失败整批记 failed。

### 21.3 插件进程收割：会永久挂死，且无上限缓冲

`_reap` 用 `communicate()`，两个问题都不是理论的：
1. `communicate()` 等的是**管道 EOF**，不是子进程退出。浏览器类插件 fork 出的 chromium
   继承着同一对管道，直接子进程被 kill 之后孙进程还攥着写端 → 超时分支里那句无参
   `communicate()` **自己挂死在收割线程里**：令牌不作废、卡片永远停在「执行中…」、
   浏览器进程组泄漏。改成 `wait()`（只等子进程）+ 可放弃的排空线程 + `_kill_tree`。
2. `communicate()` 全量存内存，而插件日志走的正是 stderr。改成只留末尾 256KB
   ——按插件约定有用的东西（结果 JSON、报错栈）恰好都在尾巴上。

`_kill_tree` 杀的是**子进程自己的进程组**（`start_new_session=True` 让它成为组长），
并且写了三重保险：`pgid` 必须等于 `proc.pid`、必须不等于本进程的组、异常全吞。
不满足就只杀单个进程并 `log.error`。**全程不涉及任何按名匹配。**

### 21.4 `plugin.toml` 写坏 → 插件静默消失，还绕过护栏

`discover()` 对 TOML 解析失败直接 `continue`，零日志。三层后果，一层比一层糟：
插件凭空不见 → 它的库内配置被当成孤儿、卡片写「插件目录已不在」而目录还在 →
`forget_plugin` 的护栏正是「discover() 里还有没有它」，于是**一个只是打错了个引号的插件，
它的授权和账号可以被一键清掉**。改成合成一条带 `manifest_error` 的清单
（id 从目录名推，约定就是 `soroban-plugin-<id>`）并记 warning。
`manifest.parse` 的文档串本来就写着「坏清单不静默消失」——只是语法错这条路径漏了。

### 21.5 OCR 三条

- **只卡字节不卡像素**：`MAX_OCR_BYTES` 卡的是**压缩后**大小，而 PNG 对纯色的压缩比能到
  几千倍。189KB 的 13000×13000 PNG 解出来 507MB，加引擎前处理峰值 1.1GB。
  更狠的是**解码在 `_infer_lock` 外面**，40 路并发就是 40 份位图同时在内存里（线性叠加）。
  两处修：`_decode_image` 惰性读 `.size` 卡 40MP（`Image.open` 不解码像素，判断零成本）；
  `run_ocr` 加**独立的** `CapacityLimiter(2)`。
  ⚠️ 写法有坑：`run_in_threadpool(fn, data, limiter=...)` 会把 limiter 当成 fn 的关键字参数
  传下去（TypeError），必须走 `anyio.to_thread.run_sync` + `partial`；也不要去替换
  `run_in_threadpool` 这个名字——`contextmanager_in_threadpool` 也走它。
- **`_same_row_value` 的向下兜底没有距离上限**：本行的号被断成两截时，它会一路扫**整页**，
  实测跨 2200px 抓到页脚的 11 位手机号当快递单号——而 11 位纯数字正好落在中通/韵达单号的
  长度区间，`Order.express_no == no` 会精确命中并把货挂到别人的订单上。
  加 `row_tol × 2` 的上限。**不能干脆禁用兜底**：真实截图存在「列头在上、号在下一行」的
  表格版式，禁用会把那种版式整页打空。
- **抽不出号 → 静默丢弃**：循环只在取到号时 append，「看见锚点却没取到号」零出口。
  3 行坏 1 行的截图只会得到 2 个号，前端照样弹绿色的「已关联 2 单」。
  加 `unreadable` 计数一路到 schema 到 toast；顺带把一直存在却从未渲染过的
  `express_nos`（注释写着「供人工核对」）拼进提示。

### 21.6 连接池：一条 `.first()` 和一个默认值

- **`latest_stored()` 漏了 `LIMIT 1`**。`.first()` 只是「取结果集第一行」，**不往 SQL 加
  LIMIT**——整张 `fxrate` 会先被排序、传输、构造成 ORM 对象再丢掉。而 fxrate 是
  **只增不删**的（一天多条），侧栏、看板、每一次建单都走这里，代价随使用时长线性增长。
- **连接池吃的是 SQLAlchemy 默认值 5+10=15**。`get_current_user` 依赖 `get_session`，
  而 FastAPI 的生成器依赖开到**响应发完**——每个在飞请求都攥着一条连接，包括一个字节
  DB 都不碰的 OCR 请求（整段推理期间）。而同步路由跑在 anyio 的 40 令牌线程池上。
  并发 40 路 OCR 实测：响应 7ms → **6220ms（174 倍）**，30 秒后抛 `TimeoutError` 漏成裸 500。
  显式配成 20+20=40 对齐线程令牌，并给 `sqlalchemy.exc.TimeoutError` 补 503 + Retry-After。
  ⚠️ 内存 SQLite 用的是 `SingletonThreadPool`，**不接受** `max_overflow/pool_timeout`
  ——一刀切传下去会让 `DATABASE_URL=sqlite://` 在 `create_engine` 就 TypeError。

  ⚠️ 这只是**止血**。根因是「OCR 路由在推理期间持有 DB 连接」，正解是让它不持有，
  但那要改 `get_current_user` 的 session 生命周期（影响每一条路由），本轮没做。见 T14。

### 21.7 前端：四页共有的同一个缺口

`rows.unshift(created); total++` 在四个列表页各写了一遍，于是同一个缺口以不同形态露出来：
筛「已送达」时新建一条「打包中」照样插到首位、分页条显示一个后端在任何查询下都给不出的
总数、刷新即消失（像没存上）；停在第 3 页时新建，新行插在第 3 页；只有商品订单页做了
`sortRows`；而删除时**只有商品订单页做本地剔除不重拉**，被顶上来的那条在刷新前哪一页都
看不到。收敛成 `frontend/src/utils/listRows.js` 的 `afterCreate/afterDelete`，四页共用。

口径（B4 拍板项，本轮按「保留筛选 + 说清楚」实现）：没有任何筛选且停在第 1 页 → 本地插入
+ 归位 + total+1（零请求）；否则回第 1 页重拉，让**后端**决定它该不该出现。
**拉完发现它不在列表里，才提示**——不预判，所以提示永远是真的。

**集运页「绑定快递单」的全局单闸**：`if (bindBusy.value) return`，而 `bindBusy` 存的是行 id、
只被当布尔用。A 行识别中往 B 行拖图 → B 行照样亮绿环、光标 pointer、松手看起来一切正常，
而那张图**一次请求都没发**、零提示；紧接着 A 行完成还弹一句绿色的「已关联 N 单」。
`@drop.prevent.stop` 的 `.stop` 又挡住冒泡，图连整窗队列都进不去，是彻底销毁。
改成排队（复用同文件已有的 `pkgQueue` 写法），`bindBusy` → `bindingRowId` + `isBinding(row)`。

### T9 · 打包版的 `inherit` 插件怎么活（**汇率在分发包上必然失败**）

这是本轮唯一「功能整块不可用」的问题，但三条路都有代价，得你选。

链路：`plugin.toml` 写 `python = "inherit"`（跑在核心解释器里、直接 import httpx），
而 PyInstaller 冻结后 `_base_python()` **只**去 `which python3/python` —— 要么落到系统
Python（没有 httpx，`ModuleNotFoundError`），要么落到 exe 自己（被 `run.py` 的 argv
白名单顶回来，报「soroban 不接受命令行参数」）。子代理用仓库 spec 真打了包（112MB）
端到端复现了两种死法。
而 `33f4f71` 之后汇率插件是**唯一**汇率来源 ⇒ 打包版拿不到汇率 ⇒ 全部 `jpy_auto` 停摆。

- **(a) `run.py` 加内部动词 `--run-plugin <dir> <entry...>` + `runpy`**（我倾向）。
  唯一能兑现 plugin.toml 里那句承诺的做法，打进包的 httpx 才真的可用。
  代价：插件被限制在「打进包里的依赖」内（httpx 够用，以后加 lxml 就得重打包）。
- **(b) 冻结态不再回退系统 Python，fx 改走独立 venv**。诚实，但直接违背
  「不能让『Windows 装不上 venv』变成『记不了账』」的设计初衷。
- **(c) 把汇率抓取搬回核心**（撤销 `33f4f71` 的一部分）。最稳，但推翻上一次的架构决定。

**无论选哪条，这两件我建议无条件做掉**（即使 (a) 出问题，你至少看得见失败原因）：
① `probe_needs` 对 `inherit` 插件改成**真去 import** 声明的模块。现在 `fx` 没有
`requirements.txt` → needs 恒为 `[]` → 卡片**谎报** `installed=true`；
② 子进程 stderr 的尾巴带到卡片上（**本轮已做**：`_summarize` 的 `errtail`）。

### T10 · OCR 像素上限取 40MP 是否合适、超限怎么办

本轮按「直接 400 拒绝」实现（`MAX_OCR_PIXELS = 40_000_000`，约 8000×5000）。
理由：降采样会掉小字体识别率，而**识别错的快递单号比识别不出来贵得多**——
错号会去精确匹配并挂靠到别人的订单上（见 21.5 第二条）。
但手机长截图拼接、A3 扫描件可能超限。要不要改成「超限降采样再识别」，你定。

### T11 · 「新建的记录不在当前筛选内」的产品语义

本轮四页统一成：**保留筛选 + 重拉 + 拉完确认它确实不在列表里才提示**。
另一条路是像商品订单页的 `focusId` 那样**清掉筛选**——新单一定看得见，但用户精心设的
筛选被清了且不可撤销。四页必须统一，别一页一个样。

### T12 · 「金额尾差」这条自动物品行的名字与形态

现在是 `<首件名>（金额尾差）`、数量 1、`auto=True` 灰显。它保证了总价守恒，
但**会让物品条数 +1**（只在除不尽时出现）。
另一种做法是不加行、把余数并进首件（那就得允许「单价×数量 ≠ 该行金额」，
会破坏「物品是最小单位」这条公理）。我选了前者，但名字/是否显示可以再议。

### T13 · `data:own` / `PluginRecord` 仍无任何删除路径（T5 的续）

`DELETE /api/plugins/{id}/config` 只删 `PluginConfig`，`PluginRecord` **全表没有任何删除
入口**。后果：卸载插件后它的私有数据永久残留；以后放一个**同 id** 的插件进来
（别人写的、或被改过的），它会静默继承前一个插件的全部私有存储。
T5 里问过一次，本轮再次命中。要么在 `forget_plugin` 里连带删，要么给个显式的清理入口。

### T14 · OCR 路由持有 DB 连接：止血 vs 根治

本轮做的是止血（显式配池 20+20、补 503 handler）。根治是让 OCR 路由在推理期间**不持有**
DB 连接——给它换一个不吃 `get_session` 的鉴权依赖，或让 `get_current_user` 查完 User
就结束事务还池，而不是靠生成器兜到响应结束。
这是**结构性改动**（影响每一条路由），且审计的两个证伪 agent 都**没有**验证过它能否在
FastAPI 依赖体系里干净落地。要不要排期做，你定。

### T15 · `_extract_tracking` 会把断行的号截成半截（本轮**未修**）

```
_extract_tracking('快递单号 SF1234 56789012', 8) → '56789012'    ← 半截号
_extract_tracking('快递单号 SF123456 789012', 8) → 'SF123456'    ← 半截号
```
这时**不走**兜底（21.5 那条上限管不到），直接把半截号当完整快递号返回去匹配订单。
候选修法：对拼接候选做长度合理性校验，或「取到的号明显短于同页其他号」时发信号
（并进 `unreadable`）。没修是因为「真实 RapidOCR 会不会在长数字串中间插空格」
**始终是假设**——`backend/.venv` 里没装 rapidocr/pillow，全部复现都是打桩引擎 +
合成 token；仓库里也没有任何集运截图样本可供回归。要不要按假设先加保护，你定。

## 二十七、第 3 轮 —— 先清上一轮遗留（步骤 0）

上一轮记为「已确认未修」和「待拍板」的条目里，凡是**修法无争议**的都做掉了。

### 27.1 打包版的三条失败路径：用户什么都看不到

打包版是**双击运行**的，任何异常都让控制台窗口在几毫秒内关掉——用户看到的是「点了没反应」。
而这三种失败恰恰都是他自己能解决的，前提是得看见错在哪。

- **端口占用**（双击了第二次）。原先：先打印「soroban 已启动」→ uvicorn 抛异常 →
  窗口关闭。**最后留在屏幕上的那句话是「已启动」，与事实完全相反。**
  改：serve 之前先探一次端口，占用就给人话 + 建议（`BACKEND_PORT=8621`）；
  那句话也改成「正在**启动**」——真正的「已启动」交给 uvicorn 自己的
  `Uvicorn running on ...` 说。实测：退出码 1，stdout 里再没有任何「已启动」。
- **安装目录不可写**（放进 `C:\Program Files\` 后双击）。`ensure_env` 的 `write_text`
  原先抛裸 `PermissionError` traceback。这条**不能吞掉继续跑**：没有 .env 就没有随机
  SECRET_KEY，而默认值写在公开仓库里 = 任何人都能伪造管理员令牌。
  改成 fail-closed + 一句可照做的话（「移到桌面或 D:\\soroban」）。实测两条不可写路径均命中。
- **其余一切异常**（迁移失败、库损坏、SECRET_KEY 校验不过）。`__main__` 加了兜底：
  打印完整堆栈 + 冻结态下 `input()` 挂住窗口。源码运行不 pause（会卡住 CI）。

### 27.2 打包机缺 OCR 依赖 → 发出去的 exe，OCR 是死的

`collect_data_files("rapidocr_onnxruntime")` 与 `collect_submodules(...)` 对**装不上的包
只发一句 WARNING 并返回空列表**，PyInstaller 照常出包。用户拿到的 exe 每次上传截图收 503，
而这个故障在打包日志里只是几百行输出中的一行黄字——只有到了用户手里才会暴露。
（更糟的是那句报错让用户「在 backend 下 pip install」，而分发包里根本没有 backend 目录。）

守卫放在 **spec 里**（硬 `SystemExit`，手动跑 spec 也覆盖），`pyinstaller.bat` 的依赖哨兵
也补上这两项让它更早失败。两条都加了元测试钉住。

### 27.3 VERSION 一改，账本就留在旧版本目录里

`%RELEASE%` = `Releases\<VERSION>` **同时是运行时数据目录**（脚本注释已经保证「绝不删它」，
但没覆盖这个场景）：VERSION 是手工编辑的常量，改了就是一个**全新的空目录**，
新 exe 首启会建一个空账本 + 新 SECRET_KEY，用户读作「升级把我的数据弄丢了」。
数据其实还在上一版目录里——但没有任何地方说这件事。
打包脚本末尾加了检测与醒目提示（列出要搬的 `soroban.db / -wal / -shm / .env / plugins\`，
并说明 .env 里的 SECRET_KEY 丢了会导致所有人登出 + MySQL 连接串解不开）。
**是否改成版本无关的数据目录仍待拍板**（见 T16）。

### 27.4 `PluginRecord` 现在会被一起清掉（原 T13）

`DELETE /api/plugins/{id}/config` 只删 `PluginConfig`，私有存储**没有任何删除入口**。
后果不是占空间，而是：以后往 `plugins/` 里放一个**同 id** 的插件（别人写的、或被改过的），
它一上来就能读到前一个插件攒下的全部私有数据——用户从没批准过，界面上也看不见。
「清理残留」的语义就是把这个 id 恢复成「从没装过」，所以两者必须一起删。
响应新增 `records_removed`。

### 27.5 半截快递号不再交出去（原 T15）

上一轮把它记成待拍板，理由是「真实 RapidOCR 会不会在长数字串中间插空格」只是假设。
**但保护本身不依赖那个假设**——不管什么原因产生了半截号，把它拿去
`Order.express_no == no` 精确匹配并原子挂靠都是危险的（撞上别人的单号就是把货挂错，
且 `version` 已 +1、不可撤销）。

判据做得很窄：**取到的号短于 10 位（主流快递单号的长度下界）、且左右紧邻着另一段
含数字的字母数字串（只隔一个空格）** → 判为读不出。
- `快递单号 SF1234 56789012` → None（原先返回后半截 `56789012`）
- `快递单号 SF123456 789012` → None（原先返回前半截 `SF123456`）
- `快递单号 12345678` → **照常返回**（孤立的短号，没有断开的证据，不误伤）
- `快递单号 SF1111111111 2026-08-01` → 照常返回（日期用连字符，不触发）
返回 None 之后这一行落进上一轮加的 `unreadable` 计数，用户会看到「另有 N 行未能读出单号」。

### 27.6 性能三条：**实测后决定不改**

上一轮审计报了三条性能问题（`/api/items` 首页全表连接排序、订单模糊搜索的 EXISTS 子查询、
`is_delete.is_(False)` 在 MySQL 上不可 sarg）。这一轮先量，再决定。

**先证伪了第三条的前提**：`.is_(False)` 在 MySQL 上确实编译成 `is_delete IS false`
（而非 `= 0`），但——**全库一根「is_delete 打头的复合索引」都没有**（逐表 `SHOW INDEX`
核对过：orders / orderstaging / shipmentorder / miscexpense 上的 `is_delete` 全是单列索引）。
没有那样的索引，就谈不上「用不上」。真 MySQL 上 20000 行实测 `IS false` / `= 0` / `= false`
三种写法耗时一致（3.6–3.8ms）——因为 `is_delete=0` 命中 99%+，优化器**正确地**选择全表扫。

**再量了另外两条**（SQLite，8000 单 × 2 物品 = 16000 物品行）：

| 查询 | 耗时 |
|---|---|
| `/api/items` 首页 count | 3.2ms |
| `/api/items` 首页取 50 行 | 9.1ms |
| `/api/orders?q=…` count（EXISTS 子查询） | 12.9ms |
| `/api/orders?q=…` 取 30 行 | 15.3ms |
| `/api/orders` 首页取 30 行 | 6.5ms |

**结论：不改。** 个人代购记账一年几百到几千单，最慢 15ms。为一个测不出来的收益去改
21 处 `.is_(False)`、加复合索引，换来的是真实的回归风险。
（上一轮的证伪 agent 也独立推翻了第三条的修法：「按它加索引，问题一点没解决」。）

**什么时候该回来改**：数据量上到百万行级，或者要给列表页加 `(is_delete, date, id)`
这类复合索引时——那时 `.is_(False)` 会真的挡住它，且 `== 0` 是干净的替代
（`== False` 会被 flake8 的 E712 拦，`sa.not_()` 生成的 `NOT is_delete` 同样不可 sarg）。
这段话写在这里，是为了让将来的人不必重新做一遍这次测量。

## 二十八、第 3 轮 · 主系统与插件的关系（步骤 1）

### 28.1 先确认一件事：核心已经不碰外部数据了

全仓 grep：`app/` 下（除 `routers/plugins.py` 起子进程之外）**一行 httpx / requests /
urllib.request / playwright 都没有**。上一轮那次「汇率搬出核心」是彻底的。

### 28.2 现在只有一种插件形态，这是不是最优解？

形态是「fire-and-forget 子进程 + 一次性令牌 + HTTP 回灌」。它的隐含前提是：
任务批量异步、可以慢、结果一行 JSON 说得清、付得起每次「起进程 + 加载依赖」的代价。

**结论：对今天的每一个候选，它都是对的；缺的不是第二种形态，而是成文的判据。**

`OCR 无法插件化` 这个判定（上一轮得出）值得追问一句——它是不是暴露了形态的缺失？
是，但**现在不该补**。OCR 是唯一一个把前四条前提全部踩反的能力：用户拖了张图正在等
（同步）、模型加载秒级且必须常驻（重量级状态）、不碰外部凭据、失败不是常态。
为它造第二种形态（长驻进程 + 双向 RPC + 进程探活 + 非一次性令牌）会把整套机制的
复杂度翻倍，而候选只有一个——那是过早泛化。
代价是诚实的：核心因此背着 rapidocr + pillow + onnxruntime，是打包体积的大头。

真正缺的东西是**判据**：今天没有任何地方写着「什么该做成插件」，下一个人加能力时只能猜。
已把判据表写进 `plugins/README.md`（五个问题：要不要外部凭据 / 失败是不是常态 /
能不能异步 / 有没有重量级常驻状态 / 核心愿不愿背它的依赖），并写明**什么时候才该造
第二种形态**：出现第二个同类候选时。

### 28.3 权限模型：两处结构性缺口，都补了守卫

`ingest` 通道是「一条路由服务 N 种数据、权限由 kind 决定」。判权在**分发处统一做**
（`handler.scope not in granted`），不在各 handler 里——所以「某个 kind 忘了判权」
结构上不可能发生。但有两个无守卫的地方：

1. **handler 声明的 scope 只校验「是不是合法 scope」，不校验「是不是最窄的那枚」。**
   把 `plugin.record` 的 scope 从 `data:own` 改成 `staging:write` 照样注册成功，
   效果是任何拿到写暂存权限的插件都能读写**别的插件**的私有存储——用户勾的是
   「写暂存订单」，给出去的远不止。代码里只是一个单词的差别，review 极易漏过。
   → 加 `test_kind_to_scope_map_is_pinned`：把 kind→scope 映射钉成一张表，改了就红
   （与 `test_consistency.py` 同一套做法）。破坏性验证过：改一个词，两条测试当场变红。
2. **`x-scope: "*by-kind*"` 哨兵的语义是「中间件只验有没有任何权限」**，真正的闸交给
   该路由自己按 kind 做。任何挂了这个哨兵、却没有第二层闸的路由，等于对所有持令牌的
   插件敞开。→ 加 `test_by_kind_sentinel_is_used_by_exactly_one_route`：
   哨兵只允许出现一次，再多一条就必须先回答「它的第二层闸在哪」。

### 29.1 【已修】我自己上一轮引入的两条回归

result = _run_engine(engine, _decode_image(image_bytes))   # ← arr 没了名字

### 29.2 【已修】`meta:read` 一直混着两类东西

它同时开着「核心元数据」（状态机规则、ingest 字段契约）和「**汇率读取**」
（`/api/fx`、`/api/fx/history`、`/api/fx/history/{on}`）。
上一轮我发现这个不一致，只把 hint 从「不含任何业务数据」改成「含历史汇率」
——那只是**让假话变成真话，混淆本身还在**。令牌收窄把它的真实代价暴露了出来。

拆开：
- **`meta:read` → baseline 权限**：每枚插件令牌无条件带上，**不出现在授权勾选框里**。
  门槛写进代码注释（新增 baseline 项前必须逐条回答「是」）：
  ① 这条路由一个字节账目数据都不返回吗？② 插件拿不到它就无法正确工作（而不是少个便利）吗？
  ③ 它是只读的吗？
- **`fx:read`（新增）**：汇率读取是业务数据，要显式授权。
- 两个插件的 `plugin.toml` 里删掉多余的 `meta:read` 声明——留着会误导（看起来像
  「用户批准了才有」，其实勾选框里根本没这一项）。

`token_scopes()` 也要并入 baseline，这是**语义要求不是顺手加的**：它同时用来算
「这条命令缺哪几项授权」（`blocked = needs - effective`）。baseline 项用户勾不到 ⇒
永远不进 granted ⇒ 任何把 baseline 项写进 `needs` 的命令，按钮会**永久禁用且无法自救**，
而 `issue()` 其实照发不误——界面说没权限，实际有。

**我的验证**（真后端 + 真浏览器）：
- 零授权的令牌读 `/api/plugins/contract` 与 `/api/meta/status-rules` → 200；读 `/api/fx` → 403；
  给了 `fx:read` → 200。
- 授权勾选框实测 3 行（`写入汇率 fx:write` / `读暂存订单 staging:read` / `写暂存订单 staging:write`）
  ——正好等于两个插件清理后的声明数，无 `meta:read`，短名都解析得出来（没有回落成裸 key）。
- 勾选 → toast「已授予「写入汇率」」→ 刷新后持久化。
- 破坏性验证：把 `issue()` 里的 baseline 并入删掉 → 3 条测试变红。

⚠️ 这里踩到过一次**假绿**：第一次浏览器复查用 `.el-checkbox` 读文字，而文字其实在外层
`<label class="grant">` 里，元素本身宽高为 0（卡片默认折叠）→ 读到空列表 →
`assert not any("核心元数据" in l for l in labels)` 恒真。空集合上的「不包含」断言永远成立，
必须先断言集合非空。

### 29.3 【已修】`_auto_provider` 说了一句很贵的假话

它只判「插件声明了 fx:write」，不看**装没装好 / 授没授权 / 开关开没开**。
于是把汇率插件停用之后，设置页仍然写着「自动获取由『汇率』插件负责」——而它永远不会再跑。
这条假话贵在：汇率取不到时账本会**继续用兜底值建单**（有值好过没值，且逐行可审计），
所以「以为它在自动更新」和「知道它停了」之间，用户的行为完全不同。

改成三态，四关全过才算数（声明 → 装好 → 授权 → 启用），差一关就说出是哪一关：
`auto_provider`（真会自动更新）/ `auto_blocked`（装了但跑不起来的原因）/ 两个都空（没装）。
不能退回「没有能自动取汇率的插件」——那对「明明装了」的用户同样是假话。

**我的验证**：真浏览器上看到提示随授权状态逐关推进——
未授权时「「汇率」还没被授权写入汇率，汇率不会自动更新」→ 勾上 fx:write 后自动变成
「「汇率」已停用，汇率不会自动更新」。四关判据真的在按顺序工作。

### 33.2 打包版的 `.env` 一直是摆设（finding #04，我实测确认）

### 33.4 汇率的两条：一条会让 422 之后数据已落库，一条让界面说了假话

**(a) `rate_for_date` 在写事务中途 `commit()`。**
链路：`stamp_fx`（订单 PATCH 中间）→ `rate_for_date` → `ensure_manual_rate`
→ `store_and_commit` → **`session.commit()`**。
后果：PATCH 后面任何一步校验失败（金额上限之类 → 422），前半截改动**已经无法回滚**，
订单价与物品从此不自洽。

值得记的是：`store()` 的 docstring **早就写过这个陷阱**（自己 commit 会击穿外层
savepoint，让通用写入通道「回执说 rejected、数据却已落库」），但当时只堵了那一条路，
而 `store_and_commit` 这个便捷包装把同一个陷阱又开了一个入口。
现在 `ensure_manual_rate` 改用 `store()`（跟着外层事务走——外层回滚 = 那张单没建成 =
这条兜底汇率行也不必留），并**删掉 `store_and_commit`**：改完它已无生产调用者，
留着就是下一个人踩同一个坑的入口。

**(b) 界面显示的汇率 ≠ 建单实际用的那条。**
`GET /api/fx` 走 `latest_stored()`（全库最新），建单走 `pick_on()`（当天**手填优先**）。
分叉场景很常见：用户今天手填 21.00，之后插件抓了一条 20.50（更晚）——
侧栏/看板/设置页显示 20.50，账本里用 21.00。
而用户手填的**本意**恰恰是「用我这个值」，显示层无视手填是这套规则里唯一说话不算数的地方。
改成 `_current_row()` = 「现在建一张今天的单会用哪条」。加了守卫测试，破坏性验证变红。

### 33.5 物品编辑器会把「正在改名的那一行」连同它的钱静默删掉（finding #35）

`saveItems` 第一行是 `.filter((it) => it.name && it.name.trim())`。
「Ctrl+A 清掉名字准备重打」期间，**任何一次其它保存**（改数量、改单价、改另一条物品）

这个坑**已经被堵过一次**：`onItemEdit` 里有 `if (!it.name.trim()) return`，
注释还写明了「saveItems 会把无名物品整条剔掉（连同它的单价）」。
但那道守卫只挡住「改这一条本身」，挡不住「改别的东西时顺带整体保存」。
**守卫必须放在所有入口的必经之路上**，也就是 `saveItems` 本身。

浏览器实测：清空第一条名字 → 改第二条数量 → 提示「有 1 条物品还没填名字」，**两行都在**。

### 35.2 关停不回收插件子进程（finding #17）

`lifespan` 的 finally 只 cancel 两个 asyncio task + `checkpoint_and_dispose()`，
**完全不管子进程**。而 `_launch` 用 `start_new_session=True` 起进程、收割线程是 daemon
——主进程一退出收割线程立刻消失，子进程却还活着，变成 PPID=1 的孤儿，
且**再没有任何人执行那个 30 分钟超时**。对浏览器类插件这意味着一个 chromium 永久留在后台：
用户「关掉了 soroban」，内存里还躺着几百 MB，而任务管理器里那个进程与 soroban
已经毫无关联，没人猜得到该去杀谁。

加了 `_ALIVE_PROCS` 注册表（`_launch` 登记、`_reap` 的 finally 注销）+ `shutdown_plugins()`：
先 SIGTERM 给 3 秒体面退出（插件可能正在写 `.state` 会话文件），再走 `_kill_tree`
（连孙进程，带三重保险）。**顺序**是先收子进程再关连接池——插件可能正在通过 HTTP 回灌，
反了会撞上已 dispose 的池、日志刷一片无意义异常。
测试起了一个**真的**赖着不走的子进程验证，破坏性验证变红。

### 35.3 `_BATCHES` 用计划数等，凑不齐就永久「执行中」（finding #21，我第 2 轮引入的）

多账号扇出的结果合并用 `total=len(fan)`——**计划**启动数。中途有账号启动失败
（缺 venv、令牌签发异常）时，实际只有 k 个子进程会回调，而这里在等 N 个：
永远凑不齐 ⇒ 卡片永久停在「执行中…」、`_BATCHES` 里那条也永不回收。
定时路径最容易命中，因为它自己吞掉单个账号的启动失败，「计划 2 个、只起来 1 个」是常态。

改成两段式：子进程各自 `_batch_add` 登记，扇出循环结束后 `_batch_seal(实际起来的数量)` 封口。
两边都判「是不是齐了」——子进程可能在封口**之前**就全跑完。
`run_command` 的循环包 try/**finally**：中途抛异常时已经起来的兄弟仍会回调，
必须保证封口执行。

### 35.4 三条「界面说假话」

- **`fx.py` 的历史窗口多算一天**：`since = today - days` + `date >= since` = **days+1** 天。
  「近 7 天」返回 8 天，看板按它算日均就偏低——而这种偏差没人会察觉。改成 `days - 1`。
- **侧栏菜单漏了 `/fx`**：菜单从路由表生成（加页面自动长出来），但**顺序**靠手写的
  `ORDER` 数组，没列进去的排到最后。于是「日元汇率」一直待在「设置」后面。
  加进去，并加守卫钉住「ORDER 必须覆盖全部页面」。
- **两处假空态**（`Dashboard` / `Items`）：加载函数只有 `try/finally`，接口挂了
  Dashboard 保持初值全 0（「总支出 ¥0、暂无数据」）、Items 保持空数组
  （「没有符合条件的记录 / 共 0 条」）。而拦截器那句 toast 3 秒后就消失——
  此后与「真的还没记过账」完全无法区分。**对一个记账工具，「你的账全没了」
  是最不该让人误会的一句话。** 两页都加 `loadFailed`，让页面本身留下痕迹。
  浏览器实测：拦截接口 → 看板显示「下面显示的不是你的账本，只是初值」，
  物品页显示「加载失败——请检查网络或后端，然后重试」；恢复后告警消失。

### 35.5 本轮我自己又写出两个假绿，都当场抓回来了

1. **`test_sidebar_order_covers_every_page` 第一版恒真**：正则写成「花括号内无嵌套」，
   而路由是单行写的且内含 `meta: { ... }` → 一个页面都匹配不到 → `missing` 恒为空集。
   删掉 `/fx` 它照样绿。改成逐行匹配，并**断言解析结果非空**。
2. **看板失败态第一次没触发**：hash 路由下 `goto` 同一个 URL 不会重新挂载组件，

这两个加上第 3 轮那个「空列表上的 `not any(...)` 恒真」，是同一个模式的三次复发：
**在集合上断言「不包含」之前，必须先断言集合非空。**

## 三十六、第 5 轮 · 设计语言（步骤 8）

**用户可见文案里不许写 markdown 强调符。** Element Plus 的 message / alert / tooltip

## 修掉的问题里，值得单独记住的几类

**1. 「界面说了假话」是这个项目最密集的一类缺陷。**
汇率插件停用了却说「由它负责」；显示的汇率不是建单用的那条；OCR 漏识别却弹绿色成功；
多账号只显示最后一个成功的；接口挂了渲染成空账本；「近 7 天」给 8 天。
共同点：**代码没崩、日志也许有一行、而用户看到的是一句与事实相反的话。**

**2. 金额相关的缺陷都藏在「看起来无害的取整/取值」里。**
`build_items` 的 HALF_UP 能让整单金额翻倍或归零；`pick_from` 靠调用方排序；
`rate_for_date` 在写事务中途 commit。这三条都不会报错。

**3. 分发链（打包版）是覆盖最薄的一环。**
端口占用时最后一句话是「已启动」；Program Files 下裸 traceback + 窗口一闪而过；
缺 OCR 依赖照样出包；VERSION 一改账本就孤立；`.env` 里的端口设置根本不生效；
分发指引会把打包者自己的登录 cookie 一起发出去。

**4. 我自己在这五轮里引入了 3 个回归，全部由审计或复查抓到。**
`recognize_order` 的 `arr`（上传京东截图必崩 500）、令牌收窄导致插件自检恒 403、
`_BATCHES` 用计划数等。教训是一致的：**重构时被抽走的东西还有别的用户，
而那个用户可能在几十行之外的冷分支里。**

**5. 假绿至少出现了 8 次，其中 5 次是我自己写的。**
未来日期让过期分支永不触发；TestClient 的 `client.host` 恒为 `"testclient"`；
grep `'"status"'` 永不匹配；空集合上的「不包含」断言（3 次）；
正则匹配不到任何东西导致恒真；hash 路由不重新挂载组件。
**沉淀下来的规则：在集合上断言「不包含」之前先断言非空；测权限/签名必须走生产签发函数；
钉行为不要钉实现。**
